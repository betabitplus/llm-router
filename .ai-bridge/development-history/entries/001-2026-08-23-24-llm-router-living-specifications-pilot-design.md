# 001 — Проектирование пилота Living Specifications

**Период:** 2026-08-23 → 2026-08-24
**Источник:** `Изучение платформы Ternforge -- 6a8b6b71-d7f8-83ed-a8b5-77a6946225f9.md`

## Главное

- Пилот сознательно ограничили **только `llm-router`**. Платформенные изменения — только если без них пилот блокируется.
- Главный принцип: **одно поведение → один исполняемый путь → replay в CI и live/manual запуск без второй реализации**.
- Отказались от собственного Scenario/Runtime/Verification framework и drift-checker. Выбран стандартный стек: **Gherkin + pytest-bdd + pytest-recording/VCR + Allure**.
- Living Specifications — не новый `e2e/`. **Acceptance/specification — роль теста, unit/integration/E2E — глубина исполнения.**
- 10 старых provider-сценариев решили перегруппировать по смыслу в **7 feature-файлов**, а не переносить 1:1.
- После доказанной эквивалентности старый E2E-код, старые cassette-paths и лишние wrapper'ы должны удаляться, а не сохраняться «на всякий случай».
- Старые hand-written verification docs допустимы только временно для ещё не мигрированной части.

## Требования пользователя

- Максимум стандартных инструментов, минимум Ternforge-специфичного framework-кода.
- Gherkin должен оставаться человеческим описанием поведения, без технических деталей реализации.
- Human-facing specification должна читаться без знания pytest/программирования; строгую BDD-семантику должны enforce зрелые стандартные инструменты, а не project-specific conventions.
- Manual/live режим должен сохранять удобство VS Code/IPython и показывать **JSON, изображения, media и другие реальные результаты**, а не только PASS.
- Evidence должно быть доступно без повторного live-вызова и желательно публиковаться в GitHub Pages.
- Не создавать новые `bdd_slices`, AST-проверки, BDD registry и другие собственные аналоги того, что уже умеют стандартные инструменты.

## Граница этапа

Полную систему проектируем с расчётом на дальнейшую платформизацию, но сначала доказываем её в `llm-router`.
