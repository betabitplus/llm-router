# 059 — Нестабильный тест таймаута: подмена SDK только для своих потоков

**Период:** 2026-10-02
**Источник:** сессия Claude Code `8b8b7335-93fe-4a32-bc00-a9e75a4428e8`

## Решения пользователя

- «да, чини тест и пуш, этап Е мы пока не берем, позже им займемся».

## Что было не так

- На CI для 4d5d22b упал `test_an_async_timedout_route_falls_back_to_the_next_route`: сервер теста получил 3 запроса вместо 2. Это был полный прогон из 473 тестов на двух воркерах в случайном порядке.
  - Ответ роутера был верным. В журнале — таймаут первого маршрута. Значит, свои два запроса роутер сделал, а третий пришёл со стороны.
  - Следующие два прогона CI (3cbc822, f4ca291) прошли. Локально тест не упал.
- Проверены и отброшены:
  - медленный резервный маршрут: третьей попытки роутер не делает, запрос просто проваливается;
  - брошенная синхронная попытка, которая повторяет запрос на тот же порт: тестовый сервер не обрывает начатые ответы, попытка получает свой ответ и больше ничего не шлёт.
- **Остаётся класс, который закрыт этим исправлением.** Провайдер спрашивает адрес сервера у подменённого OpenAI SDK при каждом запросе. Подмена в тестах действовала на весь процесс. Работа, которую прошлый тест бросил по таймауту, идёт в фоне. Если она обратится к провайдеру ещё раз, пока идёт следующий тест, запрос уйдёт на сервер следующего теста и засчитается ему.
- Замер на всём наборе: потоки после своего теста оставляют 8 тестов.
  - Шесть — это потоки тестового сервера, которые дописывают задержанный ответ, около секунды.
  - Брошенные попытки (`ThreadPoolExecutor`) — только у двух синхронных тестов таймаута, тоже около секунды.
  - Gemini WebAPI держит собственные долгоживущие потоки.

## Что сделано

- **OpenAI SDK подменяется только для своих потоков** (`worker_patches.patch_openai`).
  - Поток, который работал ещё до начала подмены, принадлежит прежней работе. Его клиента подмена отправляет на заведомо пустой адрес (порт discard): соединение сразу отклоняется, до сервера теста запрос не доходит.
  - Принцип — изоляция тестов: глобальная подмена касается только кода самого теста.
  - Опыт подтверждает обе стороны: поток прежней работы получил ошибку соединения, а поток теста и основной поток дошли до сервера.
- **Сценарии таймаута считают только свои запросы.** В запрос каждого прогона ставится уникальная метка. Если число не сходится, сообщение перечисляет все пришедшие запросы с моделью и пометкой «этот прогон / другой».
- Весь набор трижды подряд в случайном порядке на двух воркерах, как в CI: 473 из 473.
- **Семантический каскад больше не падает, когда прогон мутанта заканчивается ровно на пределе времени.**
  - Проверочный прогон после правки упал: прогон тестов одного мутанта TREQ_SESSION_SERIALIZATION завершился в тот момент, когда истёк его предел.
  - Сигнал группе процессов прогона вернул EPERM, и весь этап упал. Так macOS отвечает, когда в группе остался только завершившийся, ещё не собранный лидер. Опыт на этой машине это воспроизводит: несобранный лидер → EPERM, собранный → «нет такого процесса», лидер с живым участником группы → сигнал проходит.
  - Теперь отсутствующая группа или группа из одного такого лидера — не ошибка: останавливать там нечего. Прогон, как и раньше, считается не уложившимся в предел.
  - Так же поступает `subprocess` в CPython (bpo-40550): сигнал процессу, который уже завершился, не считается ошибкой.
  - Опыт с подменой `Popen` на исходной и исправленной версии: было — PermissionError, стало — «прогон не уложился в 1 с».

## Находки для владельца

- **Синхронная попытка, брошенная по таймауту, работает в фоне до ответа провайдера.** Поток в Python не остановить, а уже отправленный запрос дойдёт и, вероятно, будет оплачен.
  - REQ_ROUTE_TIMEOUT_FALLBACK обещает только «перестать ждать», так что требование не нарушено.
  - Останавливать ли такие попытки — вопрос продукта: цена против простоты.
  - Вариант без смены поведения запроса: после таймаута брошенная попытка не начинает новых обращений к провайдеру (повторов, раундов инструментов, починок).
