# Mutation testing platform extraction manifest — llm-router P34

> Status: **active llm-router pilot migration ledger**. This document records what has been proven locally and where reusable pieces may belong **after the pilot is explicitly finished**. It does **not** authorize current platform work or rollout to any consumer.

## PILOT SCOPE GUARD — authoritative operating rule

**Until the user explicitly declares the llm-router pilot finished, all feature development happens inside `llm-router`.** Future platform owners listed in this document are a migration ledger only; they are not authorization to implement or propagate anything in those repositories.

The only allowed platform intervention during the pilot is the minimum change required to unblock a concrete llm-router experiment that cannot be performed locally. Any such exception must be recorded here with the blocker, exact intervention, why a local workaround was insufficient, future clean owner, and cleanup trigger. Otherwise: do not edit platform repositories, do not update consumer pins, do not release, do not roll out to other consumers.

Local prototype code may be deliberately ugly or repository-specific while we learn, but every temporary choice must record its likely future owner and replacement trigger here. Cleanup/migration happens only after the feature is useful and accepted live in llm-router.

## Current active-pilot acceptance state

- Current retained full mutation evidence is the canonical `docs/_build/html/mutation-results/campaign.json`; mutation adapter provenance is `p34-local-2`; mutation semantics compatibility remains `p21-local-2`; both uniquely attributable measured mutation contracts must be fresh before this checkpoint is accepted. Shared implementation scopes remain diagnostic-only and must not be promoted into Requirement/TREQ scores.
- Current portal build: **P34**. Contract Evidence is now the requirement monitor sourced from normative Requirements/Technical requirements + `docs/test-plan.md` + dedicated contract-specific Verification Profiles + retained Actual evidence; the old custom Assurance Target/Profile registry is compatibility-only.
- `REQ_INVALID_CONFIGURATION_ERRORS` now owns only its public System semantic coverage **1/1 PASS · 1/1 path** plus its existing parent-level mutation/fault assurance: Component Mutation Reach **100% PASS**, Component Mutation Sensitivity **93.5% PASS**, System Reach **87.1% PASS**, System Sensitivity **100% PASS**, and retained mutmut Test Strength **76.4% diagnostic**. Its Contract Evidence still remains **Overall FAIL** because only 4/8 required parent fault classes currently have retained challenge/detection evidence.
- The thirteen derived `TREQ_CONFIG_*` validity contracts now own their Component semantic coverage independently: collectively **13/13 criteria PASS · 16/16 paths**, with separate Verification Profiles and Fault Models. Missing child-specific fault challenges stay red and do not inherit the parent mutation campaign.
- All 17 currently executed parent + child Invalid Configuration evidence paths belong to one retained execution and are **Provenance COMPLETE / Producer QUALIFIED / Freshness CURRENT**. Producer qualification is backed by 13 executable intended-use false-green controls pinned to the current tool/code fingerprints; upstream trust links alone do not produce monitor `QUALIFIED`.
- P34 visible structure is fixed to **1. Test Coverage → 2. Fault-based Testing → 3. History**. Matrix cells and fault-group tabs switch one parameter panel; monitor states are `PASS / FAIL / N/A / UNKNOWN`; optional retained evidence stays available in drill-down/raw facts and is not surfaced as a monitor badge or state.
- Test Coverage targets come from `VC_*` criteria authored in each contract-specific Verification Profile; every criterion belongs to exactly one normative Requirement/TREQ. Actual bindings come from standard JUnit `coverage_item` properties plus same-run Allure/coverage observations and run-start input digests; Test Level, Boundary and Actual representation are derived from current runtime evidence where available. The Invalid Configuration hierarchy is complete at 14 criteria / 17 retained paths across one parent REQ and thirteen child Technical requirements rather than being inferred from whatever tests happened to exist.
- Fault targets come from the repo Test Plan's reusable Fault-based Test Model plus Requirement applicability. Every Contract Evidence profile now classifies every project fault class explicitly as REQUIRED / OPTIONAL / N/A; missing/duplicate/unknown classifications fail the profile parser instead of silently becoming N/A.
- Platform extraction remains frozen. P34 implementation is local to `llm-router`; future ownership mapping remains a ledger only.

## Non-negotiable extraction rules

1. **llm-router remains the only mutation-testing pilot consumer until the user accepts this pilot and platform parity is proven.** No other consumer gets these changes early.
2. Sphinx-Needs remains the authoritative engineering graph. Platform extraction must consume graph relationships; it must not introduce a second requirements source of truth.
3. Requirement Test Strength uses only declared requirement-linked tests. Unrelated tests may kill mutants diagnostically but must not improve the contract score.
4. Shared implementation ownership stays **N/A** until attribution is objectively resolvable; never allocate a shared score heuristically.
5. Raw score stays `killed / (killed + survived)` for covered valid mutants. Freshness, actionability, suppressions, execution health, Representation Fidelity and Evidence Producer Credibility remain separate facts.
6. MTE stays the mutant/source/test forensic UI. Ternforge pages summarize/navigate; they do not rebuild MTE controls.
7. P23 does not authorize operator filtering. Full audit must remain available; historical tuning requires broader real-world evidence.

## Premature platform spike cleanup — learnings retained, implementation discarded

A short-lived attempt was made to start future extraction before the llm-router pilot was finished. That was outside the intended operating model. The platform-side branches were deleted and all four touched owner repositories were verified back on clean `main`. **Nothing below is an implemented platform feature.** These are only findings that must not be lost when clean extraction eventually begins.

### Candidate `py-testkit` ownership — later, not now

- Generic future responsibility: mutation executor boundary, stable mutant fingerprinting, standard Mutation Testing Report Schema 2.0 production, linked-test-only attribution, and direct execution timing.
- Spike finding: adding mutmut directly to the normal testkit dependency graph conflicts with the existing DocOps/click range. The active llm-router pilot therefore keeps mutmut out of normal dependencies; when the engine is absent, `.ai-bridge/build-mutation-report-prototype.py` relaunches itself in an isolated `uv run --with mutmut==3.8.0` overlay while preserving the project environment.
- Spike finding confirmed in the active pilot: mutmut 3.8 reads its config during import, so the runner prepares temporary config before importing engine internals and restores repository state in a parent-owned `finally`.
- Historical spike proof worth retaining: the extracted prototype reproduced the then-current three llm-router scores exactly (61/41 = 59.8%, 51/49 = 51.0%, 28/3 = 90.3%) while keeping report tests/`coveredBy` inside declared linked tests. The Invalid Configuration contract has since expanded to a 16-test mutation-linked scope and now measures 84/26 = 76.4%; future extraction must reproduce the current denominator rather than treating the historical spike score as canonical.
- **Current status:** no py-testkit mutation implementation is retained; the premature local branch is deleted. The llm-router-local runner now owns isolated engine bootstrap plus full/diff execution for the remainder of the pilot.

### Candidate `ternforge-infra-ci` ownership — later, not now

- Generic future responsibility: full/diff orchestration, previous-state retrieval, retained run/baseline history, immutable run provenance, cache/artifact lifecycle.
- Spike finding: reuse and audit evidence have different roles — cache is suitable for previous-state reuse, while a normal artifact is suitable for retained downloadable evidence. Any future extension should be default-off and stay inside the existing required CI lifecycle rather than creating a second mutation-specific workflow.
- Real llm-router retained state already demonstrates a baseline chain crossing full and diff campaigns without self-baselines.
- **Current status:** no infra-ci mutation extension is retained; the premature local branch is deleted. During the pilot, llm-router keeps local history under generated mutation-results.

### Candidate `py-policy` ownership — later, not now

- Generic future responsibility: structural validation only, not scoring or graph ownership inference.
- Critical boundary: Sphinx-Needs remains the authoritative ownership graph. Future policy should consume graph-derived facts rather than parse `@impl` independently or create a second mapping.
- Invariants learned: only uniquely attributable scopes may carry a requirement-level score; shared implementation scopes stay N/A; suppression requires contract + mutant fingerprint + non-empty reason, with optional nonblank owner and valid nonexpired expiry; suppressions affect actionability, never raw score.
- Spike proof worth retaining: llm-router's three unique measured facts plus the two shared ownership pairs validated cleanly; deliberately attributing the shared route scope produced the expected shared/N/A rejection.
- **Current status:** no py-policy mutation implementation is retained; the premature local branch is deleted. Local llm-router prototype remains authoritative for the pilot.

### Candidate `ternforge-tooling-docops` ownership — later, not now

- Generic future mutation responsibility: native Sphinx/PyData Test Strength, Mutation Analysis, measurement-coverage projection and versioned MTE static dependency/wrappers. **Contract Evidence is separate traceability/assurance UX and must not be used as a mutation detail page.**
