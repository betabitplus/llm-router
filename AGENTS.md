Engineering work is anchored in the engineering graph, not in tests or code in isolation. When the answer is genuinely unknown, investigate first and turn only durable conclusions into authoritative artifacts.

- Use `experiments/` for focused manual probes when feasibility or provider behavior is uncertain. Probe code is laboratory equipment, not production evidence.
- Preserve a durable experimental result as one self-contained `EXP_####` capsule under `experiments/<project>/exp_####_<slug>/`. A capsule owns `src/experiment.py`, one authoritative `report/report.ipynb`, its causal `inputs/`, optional retained `artifacts/`, and its own `pyproject.toml`, `uv.lock`, and `.python-version`. Reports read Question → (Step → captured Evidence)+ → Conclusion and may contain rich Jupyter MIME outputs. Capsules must not import production code, tests, sibling experiments, or shared experiment helpers. Capture from an isolated temporary copy, record the capsule digest, and render stored outputs through MyST-NB with execution disabled. Use `informs` only to link the result to an ADR, Requirement, or Technical requirement; experiments never `verify` contracts.
- Author Goals, Capabilities, Requirements, and optional Technical requirements in the docs graph. Internal `feature`/`treq` type names remain implementation details; Gherkin Feature keeps its standard BDD meaning.
- Record significant architecture choices as `ADR_####` Architecture Decision needs in `docs/decisions/`; ADRs explain why and never substitute for Requirements or Technical requirements.
- Keep ADRs minimal: Context, Decision, Consequences, and Alternatives considered. Use `affects` for material impact and a new accepted ADR with `supersedes` when a decision is replaced.
- If an ADR creates an enforceable invariant, capture that invariant as a Technical requirement; implementation and tests trace to the technical requirement, not to the ADR.
- Declare the minimum required evidence with `required_evidence`.
- Link pytest evidence with a revision-pinned `verifies` reference (`REQ_ID[revision==N]`) and an explicit `verification_kind`.
- Capture objective execution facts through `py-lib-testkit` and standard retained artifacts (JUnit, Allure, coverage.py contexts) when available. Publish `substitute`, `replay`, or `direct` boundary interactions only when that relation was actually observed; a verification-kind label never implies external reach. For Property verification, retained Hypothesis runtime evidence establishes generated execution while source-declared strategies are enrichment only. Do not infer verification scope or assurance from test directory names or source inspection when runtime evidence can provide the fact directly.
- Link implementation evidence in source with a revision-pinned target: `# @impl Title, IMPL_ID, [REQ_ID[revision==N]]`.
- Use ubCode/`ubc` for fast graph navigation, queries, references, and impact analysis when available; Sphinx-Needs remains the authoritative graph.
- When ubConnect is licensed, use GitHub Issues only as tracking mirrors via the typed `issue` field; do not import Issues as authoritative requirements.
- Treat `llms.txt`, `llms-full.txt`, and generated page Markdown as derived agent-readable views of the built documentation, never as editable engineering sources.
- Do not invent requirements merely to justify existing tests or implementation.
- Do not infer verification kind from test directory names.
